# Definição de Pronto — Code&Ops — Sprint 3

Versão proposta para adoção pelo grupo. O documento está preparado; sua aprovação coletiva ainda não foi registrada.

## Finalidade

Uma tarefa só vai para **Concluído** quando os critérios de aceitação do card e os critérios aplicáveis abaixo forem atendidos. Uma tela desenhada sem navegação não conclui uma tarefa que exige um fluxo navegável.

## Critérios comuns

- [ ] O resultado atende ao requisito e aos critérios de aceitação do card.
- [ ] O card identifica o responsável real, o resultado entregue e a evidência (arquivo, frame, link ou commit).
- [ ] Não há pendência que impeça o uso ou a avaliação do resultado.
- [ ] Outro integrante revisou o resultado; nome, data e observações estão registrados. Enquanto não houver revisão, manter em **Em revisão**.
- [ ] Documentos relacionados foram atualizados e os links foram conferidos.
- [ ] O status do card representa a situação real do trabalho.

## Para telas e fluxos no Figma

- [ ] Telas seguem o contexto Code&Ops: detecção de EPIs e acompanhamento de conformidade.
- [ ] Textos, contraste, hierarquia e elementos de navegação foram revisados.
- [ ] Botões do fluxo funcionam, incluindo retorno e cancelamento quando aplicáveis.
- [ ] Estados previstos no aceite foram representados e verificados (sucesso, vazio, erro ou validação).
- [ ] Dados de demonstração estão identificados; não há alegação de integração ou inferência real.
- [ ] Mudanças em relação à versão anterior têm justificativa no README e vínculo com requisito.
- [ ] Resolver uma ocorrência não altera retroativamente o resultado da detecção nem declara o trabalhador APTO.

## Para arquitetura e documentação

- [ ] Componentes, responsabilidades, fluxo de dados e decisões estão coerentes com os requisitos.
- [ ] Propostas estão diferenciadas de recursos implementados ou testados.
- [ ] Não há reconhecimento facial, identificação nominal de trabalhadores ou controle físico de acesso no escopo.
- [ ] A meta de precisão superior a 90% é tratada como requisito, não como resultado comprovado sem medições.
- [ ] O arquivo foi publicado no repositório e está referenciado quando necessário.

## Para cerimônias

- [ ] Data, participantes reais, formato e decisões estão registrados.
- [ ] Planning registra objetivo, itens selecionados e responsabilidades aceitas.
- [ ] Daily registra progresso, próximo passo e impedimentos reais.
- [ ] Review registra o que foi demonstrado, aceito e deixado pendente, com feedback.

## Para a entrega final

- [ ] GitHub contém README, justificativas, arquitetura, backlogs, DoD e registros das cerimônias.
- [ ] Figma contém pelo menos duas novas telas ou fluxos justificados e avaliáveis.
- [ ] Trello possui as cinco colunas exigidas e cards contextualizados com responsáveis e status reais.
- [ ] Links de GitHub, Trello e Figma foram testados com acesso de visualização adequado ao avaliador.
- [ ] O único arquivo de submissão é um `.txt` íntegro com nomes, RMs e os três links.

Critérios não aplicáveis devem ter justificativa no card. Este checklist não é evidência de que as verificações já foram realizadas.
